一段 SQL 离开表结构、数据分布和访问模式，很难被准确判断。让 AI 帮忙之前，先把问题范围整理清楚，往往比再补一句“请仔细分析”更有用。

## 先提供足够的上下文

提供经过脱敏的表结构、索引、查询目标和版本信息。遇到性能问题时，加上执行计划，比只贴 SQL 更有帮助。

说明哪些条件不能改，例如返回语义、排序要求、事务边界和应用兼容性。不要把生产连接信息或真实个人数据放进提示词。

## 要求依据，而不是一句结论

让模型区分已知事实、假设和还缺少的信息。建议越具体，越容易验证，也越容易发现误解。

```text
请审查这条 SQL，先不要重写。
1. 复述查询的返回语义。
2. 列出你能确认的问题与依据。
3. 单独列出缺少上下文的假设。
4. 为每个建议给出验证步骤。
不要执行 SQL，不要猜测实际耗时。
```

## 最后回到数据库验证

模型输出是一份待验证的建议。使用样例数据检查返回结果，用可控环境中的执行计划检查工作量变化。

先确认语义，再评估性能。一个看起来更漂亮、却悄悄改变了 NULL 或重复行处理方式的改写，不能直接合入。
